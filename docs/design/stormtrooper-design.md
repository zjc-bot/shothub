## 0. 修正摘要

### 0.1 第一轮：10 部件方案的几何硬伤

初版方案（GPT 产出）的拆分思路正确：10 个 AABB 部件承载"头盔/胸甲/肩甲/腰胯/四肢/爆能枪"六个视觉符号，
用颜色块而非增加几何体表达细节，只有 2 个部件投影。**这些判断全部保留。**

但用本项目引擎实测后，初版有 4 处硬伤，本文档逐条修正。

| # | 问题 | 实测证据 | 修正 |
|---|---|---|---|
| 1 | 脚底悬空 | `y=0.47, h=0.72` → 底边 0.47−0.36 = **0.11m** | 腿 `y=0.36, h=0.72` → 底边 0.00 |
| 2 | 下半身无命中盒 | 躯干盒 `y=1.24±0.31` → 仅覆盖 0.93~1.55；侧向射 y=0.40 实测 **MISS（穿透）** | 躯干盒下沿补到 0.00 |
| 3 | 枪在身后 | `z=-0.25`，但本项目约定 **局部 z 正 = 角色前方**（现有 bot 枪 `z=+0.42`） | 枪 `z=+0.38`，并改回右手持握 |
| 4 | 肩甲与手臂穿模 | X 重叠 0.17m、Y 重叠 0.155m、Z 重叠 0.04m | 穷举后定 y/x（**该结论在第二轮被推翻，见 0.2**） |

> 修正原则：**视觉尺寸可以变，命中盒与物理体不能退化**。
> 命中盒下沿补到 0 是唯一必须动 combat 数值的地方 —— 现有 bot 的躯干盒本就覆盖 0~1.80，
> 暴风兵不能比现有角色更容易被打穿。

### 0.2 第二轮：26 部件版，**只有渲染才能发现的 4 处硬伤**

10 部件版满足不了"层叠装甲"的要求（白甲之间没有黑色内衬做接缝），
于是扩到 26 部件：黑色内衬 `core` + 白色胸甲 + 两层腹甲 + 黑色腰带 + 腰胯甲 +
宽肩甲 + 上臂/前臂/手甲 + 大��/膝甲/小腿甲 + 黑色面罩与呼吸器。

**关键教训：以下 4 处缺陷，AABB 数学验算全部"通过"，只有真正渲染出图才暴露。**
原因是数值验算的判据是我自己写的，而我写的判据本身就有漏洞。

| # | 缺陷 | 数学验算为何漏掉 | 怎么发现的 | 修正 |
|---|---|---|---|---|
| 1 | **肩甲浮空 0.051m** | 判据只查 `肩底 >= 臂顶 - 0.005`（不许陷入），**没查浮空**；而"浮空"才是肉眼可见的破绽 | 屏幕投影测量：肩甲底与上臂顶差 6.1px | 肩甲 `y 1.58 → 1.50`，压住上臂 0.035m |
| 2 | **腰部两处穿透空洞** | 只验算了部件两两关系，**没验算"整体轮廓是否封闭"** | 正对角色逐高度打射线：y 0.72~0.73、0.82~0.84 全空 | `core` 由 `h=0.60 @y=1.18` 改 `h=0.80 @y=1.08`，填满 0.68~1.48 |
| 3 | 渲染图被纵向拉伸 2.9 倍 | 纯环境问题，与部件无关 | `head` 投影成 30×**93** px（0.34 的立方体不可能这么瘦高） | 相机 `_aspect` 必须设为 `W/H` 而非默认 16/9 |
| 4 | 正/反面判断反了 | **`_rot_local(off, 0) = (x, y, -z)` —— 局部 +z 映射到世界 −Z**。我一直以为"世界 z 正 = 角色正面"，导致从背后截"正面图"，白白怀疑面罩/胸口细节位置 | 调色板渲染：背面视图却出现 visor + chest_dtl | 相机方位角 180° 才是正面 |

> **给后续的硬规则**：
> 1. 部件表改完必须**渲染出图**看，不能只跑 AABB 断言。
> 2. 轮廓类问题（浮空/空洞/脱节）要单独验，**两两关系验算覆盖不到**。
> 3. 判据要成对写：既要查"不许陷入"，也要查"不许浮空"，只写一半等于没写。
> 4. 截产品图前先确认三件事：相机 aspect、读帧缓冲在 `display.flip()` **之前**、相机方位与朝向的符号约定。

## 1. 部件表（30 部件，已实现并接入波次）

坐标系：`(x 右, y 上, z 前)`，**y 以脚底为 0**。
⚠️ **z 正 = 角色前方，但只对局部坐标成立**：`_rot_local(off, 0) = (x, y, −z)`，
即 yaw=0 时局部 +z 映射到**世界 −Z**。因此"看角色正面"的相机在**世界 −Z 侧**。

### 1.1 层叠是怎么做出来的

本项目 `box_mesh` 一个立方体只能整体一个颜色，做不出"同一件上的白甲+黑缝"。
所以用**三层不同深度的盒子**堆：

```
core    黑色内衬，z 较浅   →  从白甲边缘露出的"黑缝"
plate   白色装甲，z 较深   →  叠在 core 外侧
detail  黑色细节，最浅     →  贴在装甲板最前面
```

实测深度：core 前沿 z=0.12，胸甲前沿 z=0.18 → 外露 0.06m 黑边。

> **层叠的"接缝"靠 Z 方向深度差表达，不靠 Y 方向小重叠。**
> 最初误把"层叠"理解为相邻板 Y 方向只重叠 0.02m。实测腹部纵向只有 0.34m
> （腰带顶 0.82 → 胸甲底 1.16），穷举求解器返回 **0 组可行解** —— 数学上无解。
> 实际暴风兵腹甲本就是大幅交叠的整块，故改为 Y 正常交叠、Z 递减表达前后层次。

### 1.2 关键 key：为什么胸甲的 key 必须叫 `torso`

`bots.py` 的 `update()` 在 SPAWN 入场态**硬编码**访问 `self.parts["torso"][0]` 做入场闪烁。
26 部件表没有 `torso` 这个 key，一改名就 `KeyError: 'torso'` 崩掉。

两种解法：
1. 加别名 `self.parts["torso"] = self.parts["chest"]` —— ❌ 部件计数虚增 1，且 `_sync_parts` 会重复遍历同一实体。
2. **直接把胸甲命名为 `torso`** —— ✅ 零改动复用父类逻辑。

选 2。**教训**：换部件表时，父类里凡是按 key 字符串硬编码的地方都要重新核对一遍。

### 1.3 摆动：父类分支不能复用

父类 `_sync_parts` 按 `leg_l/leg_r/arm_l/arm_r` 四个 key 分发 pitch。
本表把它们细分为 `thigh/knee/shin` 与 `upperarm/forearm`，
因此**覆写了 `_sync_parts`**，摆动分组改为模块级 `ANIM_GROUPS`：

| 组 | 幅度 | 说明 |
|---|---|---|
| `thigh_l/r` | 25° | 与父类腿幅度一致 |
| `knee_l/r` | 12° | 递减，模拟关节链传导 |
| `shin_l/r` | 8° | |
| `upperarm_l/r` | 8° | 与父类臂幅度一致，左右反相 |
| `forearm_l/r` | 4° | |

`hand_*` / `shoulder_*` / `head` / `torso` / 腰腿其余部件**不摆动**（pitch=0）。

物理体、命中盒、AI 状态机、伤害、死亡侧倒全部**继承不改**。

### 1.4 肩甲为什么允许与上臂三轴交叠

其余各对部件都要求"不三轴穿模"，**唯独 `shoulder_*` 与 `upperarm_*` 例外**：
肩甲是罩在肩关节上的护盖，不交叠反而不对。

判据改成"必须咬住上臂"：纵向重叠需落在 **0.02 ~ 0.06m**。
`y=1.58` 时重叠为 0 → **浮空 0.045m**（肉眼可见破绽）；`y=1.50` 时 0.035 ✓。

### 1.5 比例校验

| 量 | 值 | 说明 |
|---|---|---|
| 总高 | 1.66+0.17 = **1.83m** | 与现有 bot 1.82m 几乎一致 |
| 脚底 | 0.36−0.36 = **0.00** | 贴地 |
| 头高占比 | 0.34 / 1.83 = 18.6% | 略大于现有 bot（17.6%），显头重，符合全盔特征 |

## 2. 命中盒

**与视觉对齐，但下沿必须补到地面**（修正点 2）。

```python
HEAD_OFFSET = Vec3(0.00, 1.66, 0.00)
HEAD_HALF   = Vec3(0.17, 0.17, 0.15)     # 与头部件等大
BODY_OFFSET = Vec3(0.00, 0.90, 0.00)     # 注意：不是 1.24
BODY_HALF   = Vec3(0.32, 0.90, 0.26)     # 半高 0.90 -> 下沿 0.00
```

### 2.1 为什么躯干盒用 0.90 而不是跟着躯干部件走

躯干**部件**中心在 y=1.20（只管视觉），但躯干**命中盒**必须覆盖全身下半身
（0.00~1.80），因为：

- 玩家可以打腿 —— 打不中会让"瞄下盘"完全无效，手感极差
- `combat.py` 只有头/躯干两个盒，躯干盒就是全身盒
- 爆头判定靠"头盒 vs 躯干盒谁先命中"，躯干盒太矮会让侧面射击几乎全判爆头

初版给的 `BODY_OFFSET=1.24 / BODY_HALF=(0.27,0.31,0.17)` 实测导致 y=0.40 处**穿透**，
这是必须避免的。**这组数值与现有 `HumanoidBot` 完全一致**，即不改变命中手感。

### 2.2 爆头优先补偿仍适用

`combat.py` 的 `th <= tb + 0.15` 头优先补偿逻辑不变。暴风兵头盒 y 1.49~1.83、
躯干盒 y 0.00~1.80，与现有 bot 的关系几乎相同，补偿量无需调整。

## 3. 配色

遵守 `docs/art/visual-style.md` §0 的 pastel 三原则（明度 0.60~0.95、通道差 ≤0.45）。

```python
# 白色装甲 —— 不用纯白 (1,1,1)，避免高光下失去层次
_SW_WHITE = (0.88, 0.88, 0.86)     # 明度 0.88，通道差 0.02  ✓
# 深灰"黑色"件 —— 明度下限 0.60 是硬约束，故用 0.50 配金属高光表现黑
_SW_DARK  = (0.12, 0.12, 0.14)     # 明度 0.14，通道差 0.02
```

> ⚠️ `_SW_DARK` 明度 **0.14 低于 pastel 下限 0.60** —— 这是**有意的**。
> 暴风兵的黑白对比是其唯一辨识特征，若强行提到 0.60 会变成"灰白套装"失去识别度。
> 折中做法：0.50 基色 + `shininess=72 / spec=0.70` 的强金属高光，
> 让它在 pastel 光照下仍读作"深色金属"而非"脏灰色"。
> **这是全项目唯一一处对三原则的显式偏离，需在文档与代码注释中留痕。**

### 3.1 已实现的颜色块

本项目**没有 per-face 颜色**：`box_mesh` 一个立方体只能整体一个颜色，
所以"面罩"不可能只涂在头的前面——必须增加一个贴在前面的薄立方体。
薄片要避免 z-fight：本体深 0.30 → 前沿 0.15，薄片中心须 ≥ 0.16。

| 视觉符号 | 部件 | 做法 |
|---|---|---|
| 深色面罩（眼窗） | `visor` | 头盔前贴 `0.30×0.09×0.02` 薄片 |
| 黑色呼吸栅格 | `respirator` | 面罩下方 `0.15×0.09×0.03` |
| 胸口控制区 | `chest_dtl` | 胸甲前贴 `0.16×0.11×0.02` |
| 黑色内衬（接缝） | `core` | Z 较浅的黑色大盒，被白甲包住 |
| 战术腰带 + 装备盒 | `belt` / `belt_pouch` | 独立黑色部件 |
| 肢体黑内衬 | `arm_core_l/r` / `leg_core_l/r` | 比白甲**窄**，只在白甲缝隙里露出 |

### 3.2 为什么必须压到 0.14（而不是 0.50）

着色器是 `albedo * u_ambient`（乘法），base color **线性地**压低结果，
但**感知被 gamma 2.2 强烈压缩** —— linear 0.256 只显示成约 0.54。
所以"看起来不够深"不是觉觉错觉，而是可预测的：
base color 减半，屏幕上只暗一点点。

真实渲染后测得的暗部平均亮度（正面视角）：

| base color | 渲染亮度 |
|---|---|
| 0.50（初版） | 0.648 —— 灰不拉几 |
| 0.26 | 0.526 |
| 0.16 | 0.454 |
| **0.12（现值）** | **约 0.43** |
| 0.07 | 0.365 |
| 0.04 | 0.318 |

**选 0.14 附近而不选 0.07/0.04**：再深就成了"洞"。低多边形角色
靠明暗梯度读形体，纯黑会让面罩 / 腰带失去体积感。

**spec 实测不影响暗部深浅**（spec 0.15 与 0.70 的渲染结果相同），
所以 `shininess 72 / spec 0.70` 保留不变 —— 它只负责让暗件读作金属。

| 视觉符号 | 部件 | 做法 |
|---|---|---|
| 深色面罩（眼窗） | `visor` | 头盔前贴 `0.30×0.09×0.02` 薄片 |
| 黑色呼吸栅格 | `respirator` | 面罩下方 `0.15×0.09×0.03` |
| 胸口控制区 | `chest_dtl` | 胸甲前贴 `0.16×0.11×0.02` |
| 黑色内衬（接缝） | `core` | Z 较浅的黑色大盒，被白甲包住 |
| 战术腰带 + 装备盒 | `belt` / `belt_pouch` | 独立黑色部件 |

## 4. 部件数与 draw call 预算（已用实测重新定标）

初版"10 部件 / 80 draw call"的预算是**拍脑袋定的，没有任何测量支撑**。
现已用真实 GPU 帧时间重新标定（Intel 核显，1280×720，`ctx.finish()` 强制同步）：

| 方案 | 同屏 | draw call | p50 帧时间 |
|---|---|---|---|
| 7 部件 bot | 5 | 55 | 6.81 ms |
| 7 部件 bot | 15 | 165 | 7.56 ms |
| 26 部件 | 5 | 160 | 7.89 ms |
| 26 部件 | 15 | 480 | 11.10 ms |
| 26 部件 | 30 | 960 | 15.87 ms |
| **30 部件（现状）** | **14（实测）** | **450** | **11.27 ms（p95 15.43）** |

**关键结论：draw call 不是瓶颈。** draw call 从 55 涨到 960（**17 倍**），
帧时间只涨 2.3 倍。逐项隔离测量显示真正的成本在别处：

| 实验 | 结果 | 结论 |
|---|---|---|
| draw call 55 → 660（12 倍） | 8.01 → 11.97 ms（+49%） | draw call 非瓶颈 |
| 阴影灯 2 → 0（实体不变） | 8.77 → 6.47 ms（−26%） | 阴影 pass 是大头 |
| 分辨率 1280×720 → 640×360 | 8.69 → 6.57 ms（−24%） | 填充率占约 1/4 |

> **顺带修正一个错误认知**：175 FPS（5.71 ms/帧）这个目标**本来就没达到** ——
> 光场景基线（地形/围墙/装饰，0 个 bot）实测就要 6.00 ms。
> 26 部件方案在同屏 5 个时是 7.89 ms，相对现有 bot 只慢 1.1 ms（+16%），完全可接受。

**预算重定为 400 draw call**（同屏 12 个 26 部件 bot = 384），
远在 60 FPS（16.7 ms）实测容量之内。

## 4.1 已解决：四肢关节加黑色内衬（26 -> 30 部件）

**原问题**：26 部件版的"白甲 + 黑内衬"只在面罩、腰带、胸口细节显黑，
**四肢关节一点黑都没有**，整体读作"一坨白"。实测暗部像素占比
（亮度直方图双峰：暗 0.60~0.70 / 亮 0.80~1.00）：

| 视图 | 26 部件 | 30 部件（修后） |
|---|---|---|
| 正面 | 13.2% | 14.4% |
| 3/4 | 8.8% | 12.1% |
| 背面 | 22.5% | **36.0%** |
| **平均** | 11.2% | **16.5%** |

**根因**：四肢**根本没有黑色内衬部件**（只有躯干有 `core`）。

**修法 = 加内衬 + 缩短白甲留缝，两件事缺一不可**：

- 只加内衬 → 内衬比白甲窄，被更宽的白甲**完全挡住**，还是看不见；
- 只留缝 → 四肢没有黑色底，留缝就是**空洞**（正面射线直接打穿到背景）。

新增 4 个黑色内衬（比白甲**窄**，故只在缝隙里露出，不会从侧面凸出）：

| key | 尺寸 | 偏移 | 覆盖 | 包裹的白甲 |
|---|---|---|---|---|
| `arm_core_l/r` | 0.15 × 0.55 × 0.18 | (∓0.36, 1.125, 0) | y 0.85~1.40 | 上臂(0.17/0.20) + 前臂(0.16/0.19) + 手甲 |
| `leg_core_l/r` | 0.17 × 0.70 × 0.20 | (∓0.15, 0.35, 0) | y 0.00~0.70 | 大腿(0.21/0.24) + 膝(0.20/0.23) + 小腿(0.19/0.22) |

同时缩短白甲以让出缝隙：

| 白甲 | 原 (h @ y) | 新 (h @ y) | 让出的缝 |
|---|---|---|---|
| `upperarm_l/r` | 0.27 @ 1.30 | 0.22 @ 1.325 | 肘部 0.095m |
| `forearm_l/r` | 0.25 @ 1.06 | 0.20 @ 1.020 | （同上） |
| `thigh_l/r` | 0.33 @ 0.53 | 0.26 @ 0.560 | 膝上 0.06m |
| `shin_l/r` | 0.26 @ 0.13 | 0.20 @ 0.100 | 膝下 0.05m |

**黑色内衬必须跟随它包裹的肢体摆动**（`arm_core_*` 跟 `upperarm_*` 同幅度 8°、
`leg_core_*` 跟 `thigh_*` 同幅度 25°），否则白甲一转、黑内衬留在原处，肘/膝会裂开。

**验算判据也升级了**：白甲之间的间隙不再要求"≤0.03"（那是旧的"不许脱节"），
改为**"缝必须被某个黑色内衬纵向覆盖"** —— 这比"不许有缝"更强，因为它同时排除了空洞。
三向轮廓射线复扫（正面/背面各在 x=0, ±0.15 打三条）仍**无空洞**。

## 4.2 已接入波次生成

原先 `game/waves.py` 的 `_spawn_one` / `debug_spawn` **硬编码 `HumanoidBot`**，
所以暴风兵写完了游戏里也看不到 —— 这就是"敌人的外形还是没改"的根因。

现改为 `BOT_CLASS = Stormtrooper`（模块级常量，便于将来做兵种混编）。
因为 `Stormtrooper` 继承 `HumanoidBot` 且只覆写外观，**手感完全不变**：

| 项 | 实测值 |
|---|---|
| 生成产物类型 | 14 只全部 `Stormtrooper` |
| 物理体半高 / 质量 | 0.91 / 65.0（与父类一致） |
| 命中盒常量 | `(0.0, 0.9, 0.0)` / `(0.32, 0.9, 0.26)`（仍来自 `combat.py`，未动） |
| selftest | **21/21 PASS，exit 0** |

**帧时间实测（同屏 14 只 × 30 部件 = 450 draw call）**：
p50 **11.27 ms** / p95 **15.43 ms**，占 60 FPS 预算 68%。
真实同屏上限是 5（`WAVES` 字面值 3/4/4/5/5），所以实际开销远低于此。

### 4.3 真实场景复测（**这个才是该引用的数字**）

上面那些数字是在**清空世界的合成场景**里测的，基线极低，
会让人误以为 30 部件"几乎不要钱"。真实游戏里世界本身有 94 个实体、
HUD、2 盏阴影灯，基线高得多。

| 同屏 bot 数 | bot 部件数 | draw call | p50 帧时间 |
|---|---|---|---|
| 0（空场景） | 0 | 0 | **9.99 ms** |
| **5（真实上限）** | 185 | 235 | **12.86 ms** |
| 8 | 296 | 376 | 14.38 ms |
| 14（理论值） | 518 | 658 | 16.23 ms |

**5 只 bot 的真实开销 = +2.87 ms（相对空场景 +29%）**，占 60 FPS 预算 77%。

结论没有变（30 部件在真实同屏上限下完全做得起），但**余量是 77% 不是 47%**，
如实记录以免后续据此做决策时吃亏。

> **本机核显 + 共享机器，帧时间抖动可达 25%**（同一配置连测 4 次：
> 8.04 / 9.52 / 9.67 / 10.01 ms）。绝对值不可信，**只有相对增量可信**。
> 另外测量时逐帧 `ctx.finish()` 强制同步，比真实游戏循环偏悲观。

### 4.4 激光尾迹（Tracer）

需求："敌方尾迹要有、长度稍长、红色；玩家蓝色"。

`combat.py` 的 Tracer **一直都在生成**（`bot_shoot_hits_player` 每次开火都调），
问题是**在交战距离上退化到看不见**：

| 距离 | 旧截面 0.025m | 新截面 0.055m |
|---|---|---|
| 7 m | **4 px** | 36 px |
| 12 m | 1.25 px | 2.75 px |
| 20 m | 0.75 px | 1.65 px |

旧参数下 14m 处只有 1.07 px、20m 处不足 1 px —— 加上 `LIFE=0.07s`（约 4 帧），
等于没有。**所以不是"没做尾迹"，是做了但看不见。**

现参数：

| 项 | 旧 | 新 | 理由 |
|---|---|---|---|
| `PLAYER_TRACER_COLOR` | (1.00, 0.88, 0.55) 琥珀 | **(0.30, 0.62, 1.00) 蓝** | 按阵营区分 |
| `BOT_TRACER_COLOR` | (0.95, 0.45, 0.40) 鲤红 | **(1.00, 0.16, 0.13) 红** | 原色偏粉，提饱和 |
| `TRACER_THICK` | 0.025 | **0.055** | 交战距离下可辨认（实测 9 倍像素） |
| `TRACER_TAIL` | — | **1.20** | 尾迹向枪口后方延伸，比弹道更长，读作激光束 |
| `TRACER_LIFE` | 0.07 | **0.10** | 6 帧，够眼睛捕捉 |

> 尾迹仍走 `unlit=True`，不挤 `MAX_SPOTS=3` 的灯光预算。
> 长度仍按 0.5m 档位取整 —— `box_mesh` 按尺寸缓存，量化是为了不炸网格缓存。

## 5. 与现有 bot 的并存

**不修改 `HumanoidBot`**，新增独立类：

```
game/units/
├── __init__.py
└── stormtrooper.py      # Stormtrooper(HumanoidBot) —— 仅覆写部件表
```

`Stormtrooper` 继承 `HumanoidBot`，只覆写 `__init__` 里的 `spec` 和颜色常量：

```python
class Stormtrooper(HumanoidBot):
    _SW_WHITE = (0.88, 0.88, 0.86)
_SW_DARK  = (0.12, 0.12, 0.14)     # 明度 0.14，通道差 0.02

    def __init__(self, scene, physics, app, pos_xz, hp, elite,
                 wave_damage, wave_err, wave_index):
        super().__init__(scene, physics, app, pos_xz, hp, elite,
                         wave_damage, wave_err, wave_index)
        # 移除父类建的 7 个部件，按暴风兵表重建 10 个
        ...
```

**复用父类的一切**：物理体、BODY_HALF_Y、命中盒、FSM AI、行走摆动、死亡侧倒、
受击提亮、掉落、爆头判定。**只换外观。**

### 5.1 命中盒的继承问题

父类 `HumanoidBot` 用**模块级常量** `combat.HEAD_OFFSET/HEAD_HALF/...`（全局单例），
所以任何 bot 变体共享同一套命中盒。本设计**不打算改命中盒**（修正后与现有值一致），
因此继承无冲突。若将来要做"体型不同的高瘦/矮壮 bot"，则必须把命中盒改为
**每实例字段**（`self.head_offset` / `self.body_offset`），`combat.py` 改为读实例字段 ——
那是独立的一次重构，本期不做。

## 6. 动画复用：**不成立，已覆写**

初版结论"`_sync_parts` 无需任何修改，key 命名兼容"**在多部件表上是错的**。

| `leg_l` → `+leg_swing` | leg_l | ❌ 已细分为 `thigh/knee/shin` + `leg_core` |

因此 `Stormtrooper` **覆写了 `_sync_parts`**，摆动分组改为模块级 `ANIM_GROUPS`
（详见 §1.3）。除"位置/朝向/roll/死亡侧倒"沿用父类逻辑外，

> `_muzzle` 仍沿用父类的 `off.z + 0.45` = 0.38+0.45 = **0.83**，
> 而枪口实际在 `z = 0.38 + 0.86/2 = 0.81`，差 0.02m，远小于弹道散布，接受。

## 9. 复现验算的方法

渲染验收脚本放在临时目录（不进仓库）：

| 脚本 | 作用 |
|---|---|
| `t_gpu.py` | draw call / GPU 帧时间扫描（真实窗口 + `ctx.finish()`） |
| `t_bottleneck.py` | 隔离瓶颈：阴影灯数、实体数、分辨率 |
| `t_geo.py` / `t_final.py` | 部件表几何 + 继承 + 摆动 + 配色断言 |
| `t_proj.py` | 屏幕投影测量（找出肩甲浮空） |
| `t_debug.py` | 调色板渲染（部件唯一配色）+ 三向轮廓空洞射线扫描 |
| `t_contrast.py` | 亮度直方图，量化黑白对比是否读得出来 |
| `t_render.py` | 产品级四视图 / 特写 / 行走姿态出图 |

> **截产品图的三个前提**（都踩过坑）：
> 1. 相机 `_aspect` 必须设为 `W/H`，否则画面被拉伸 ~2.9 倍；
> 2. 读帧缓冲必须在 `pygame.display.flip()` **之前**，否则读到交换后的陈旧内容；
> 3. 角色正面在**世界 −Z**（`_rot_local` 把局部 +z 映射到 −z），相机方位角 180° 才是正面。
